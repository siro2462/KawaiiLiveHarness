# 出来事を自分のこととして語れる記憶の材料（作成手順 v2）

これは記憶の**作成・点検用**の型。Surfaceの新プロンプトでも、操作列の指定でもない。
作成者が材料を記入し、CPUは参照・形式・由来を検査する。CPU検査は意味の正しさやライブ感の採点ではない。

## 抽象化で残すもの

|材料|具体的に残す内容|避けたい置き換え|
|---|---|---|
|本人の用事・望み|何を手に入れたい／どうしたかったか。いつの望みか|「充実した経験をしたい」など目的が見えない一般化|
|引っ掛かりの現物|見た物、数字、手応え、身体感覚、結果など、反応のきっかけ|「予想外の出来事が起きた」だけにする|
|その時の見立て|その瞬間に期待・解釈したこと。後の知識と分ける|後で分かったことを最初から知っていたことにする|
|直接の反応|何への喜び・苛立ち・戸惑いか。短い内心は任意|すべて「嬉しかった」「驚いた」という説明にする|
|見直した理由|どの新しい事実、比較、思い出しで見方が変わったか|根拠のない自己分析・一般論を足す|
|残る気持ち|喜びと物足りなさ、悔しさと諦めなど、両立するもの|必ず前向きに解決して締める|
|確かさと状態|実行／希望／予定、本人の推測、他人の意図の不明|予感・願望・疑念を結果や確定事実にする|

既存の望み・反応・評価・対応IDの欄を使う。新しい感情欄を増やすこと自体を目的にしない。
短い言葉は、内心・現在の言い換え候補・実際の発言の区別を残す。候補を実際の発言として引用しない。

## 選べる形

- **期待が外れる**：具体的な望み → 手掛かり → 違う結果 → 反応 → まだ残る望み。
- **同じ結果に両方の気持ち**：よかった点と物足りない点を、同じ結果に結び付ける。
- **見ていた意味が変わる**：初めの解釈 → 追加の観察 → 別の理解。相手の意図の断定とは分ける。
- **自信と現実の揺れ**：手応え → 自負 → 次の結果／別の出来事 → 評価の修正。
- **好きだから困る**：欲しい物・活動 → 行動 → 量・時間・体力の負担 → それでも残る好み。

これは選択肢で、必須の順序ではない。すべての素材に山場・疑念・教訓・今後の方針を入れない。
人間の原文にも教訓はある。出来事を受けて実際に語られた教訓は残し、数合わせでは作らない。
F/E/T比率や同じ色の最大連続数だけを合わせても、記憶の厚みを再現したとは扱わない。

## 公開投稿から場面を調べる

今どきの生活や20代の体験を題材にする依頼では、創作前にXなどの公開投稿を少量調べる。依頼の題材と対象人物像に合う投稿を選び、投稿URL・投稿日・取得日時・検索条件と、採用する場面の手掛かりをローカルに残す。

- Xはユーザーが利用を許可したログイン情報でtwscrapeを使い、取得障害があれば原因を確認してtwikitを代替にする。2026-11-07にtwscrapeで5件と10件の取得を確認した。認証・通信・検索の成否はその都度確認する。
- 「20代」という条件は、本人が投稿やプロフィールで示した年齢とその時点を確認する。検索に年齢の語が一致した件数と、対象に合う本人の体験談として確認した件数を記録する。友人・推しの年齢、周年、昔の年齢などの一致は個別に読み分ける。
- 少量の候補を本文まで読み、何をしに行ったか、何が見えた／聞こえたか、その瞬間どう解釈したか、それで次に何をしたかを拾う。写真・動画の中身を未確認なら、その部分の観察は保留にする。
- 商品名・地名は用事、手の動き、移動、選び直しに結び付ける。名称の追加や流行語の数を「今どきらしさ」の採点に使わない。
- 公開投稿を参照した内容と、作成者が加えた人物・情景・台詞・行動を記録する。投稿者の実体験をキャラクター本人の実体験として登録する根拠にはしない。
- HARやCookieを使う場合は、利用を許可されたXの認証情報を必要な範囲で読む。HAR・認証値・取得本文はローカルに保管し、公開記録には汎用手順と抽象的な所見・集計を残す。

検索結果は創作の参考材料。取得成功、題材の適合、記憶の意味保持、実発話の自然さをそれぞれ確認する。複数人の投稿を読む場合も、対象年齢層全体の代表例とは扱わない。

## 新しい創作記憶の作り方

1. 公開投稿から拾った場面の手掛かりを参考に、人物・状況・出来事を組み直した独立の創作仕様を先に書く。実在の地名・商品名や機能を使う箇所は確認先を残す。
2. 仕様に、本人の目的、観察、当時の見立て、実際に変わった評価、未解決点を必要な分だけ記す。
   本人が気づく前の行動、気づくきっかけ、その次の動作が追えるようにする。詩的な比喩や気持ちの総括で場面を埋めず、題材ごとに用事や展開を選ぶ。
3. 仕様を保存してhashを取り、そこから断片を作る。断片は語りの完成台本や期待出力にしない。
   型は抽象化しても、断片の中身は具体的に保つ。「評価が変化した」という第三者の分析より、本人が何をどう捉え直したかを短く残す。
4. 反応・評価には対象と根拠を付ける。希望には時点、予定には未実行の区別を付ける。
5. 推測の答え、他人の反応、後日の結果が仕様に無ければ不明のままにする。
6. 既存normalizerと参照検査を通す。実DBへは自動登録しない。
7. 操作列は後段のCPU選択器の仕事。作成者が「望ましい色順」に合わせて並べない。

元DBは保全する。創作仕様を人間の発話・実体験・既存DBの原文根拠として表示しない。
既存形式の「原文根拠」は創作設定では空配列とし、別の「創作仕様根拠」で対応を残す。

## 検証時の区別

- 技術：ID、根拠文字列、参照先、状態、元DBの保全、既存形式への適合。
- 手動点検：反応が本人の用事に結び付くか、見直しの前後が混ざらないか、同じ意味の水増しか。
- 未確認：CPUの操作選択、実Surface出力、読み上げの自然さ、未知の題材への一般化。

将来比較するならLoRA・指示・生成設定を固定し、変更した記憶の材料を明示する。
今回の型だけから、Surfaceの改善や人間らしさの再現に成功したとは判定しない。
